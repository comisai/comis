### Broker request fails with 407

A 407 response means the driven-CLI's proxy token was missing, forged, or already consumed (each token is single-use). The broker emits `broker:denied` with `reason: "bad_token"`.

To diagnose:
```bash
grep 'broker:denied' ~/.comis/logs/daemon.log | grep bad_token | tail -20
```

Common causes:
- The CLI was not launched through the broker (no `HTTPS_PROXY` env var set to the broker).
- The session was torn down before the request completed.
- A token was replayed (single-use invariant).

Resolution: ensure the CLI is launched via the daemon's driven-CLI spawn path (not invoked manually without broker env).

### Broker returns 403

Two `broker:denied` reasons produce 403:

- `no_binding` — the requested host has no matching `hostRules` entry. Add a binding or use a built-in preset (`anthropic`, `finnhub`).
- `path_policy` — the host is allow-listed but the path is blocked by `pathPolicy`. Check the binding's `pathPolicy` glob.

```bash
grep 'broker:denied' ~/.comis/logs/daemon.log | grep '"reason":"no_binding\|path_policy"' | tail -10
```

### Broker returns 502

A 502 means the broker could not resolve the `secretRef` from SecretManager (`broker:credential_unavailable` event emitted; request never forwarded).

```bash
grep 'broker:credential_unavailable' ~/.comis/logs/daemon.log | tail -10
# Check that the secret exists:
node packages/cli/dist/cli.js secrets list
```

Ensure the `secretRef` in the binding exactly matches the key name returned by `secrets list`.

### Broker returns 501 (WebSocket)

A WebSocket upgrade from the credentialed sandbox returns 501 with `reason: "ws_upgrade_not_supported"`. This is a fail-closed guard — WS credential injection is not supported in this release (WS-01 is future). The error is intentional and actionable rather than a silent hang.

### Tracing a full broker request

Every broker log line carries `step` (pipeline stage), `traceId`, and `agentId`. To trace a full request lifecycle:

```bash
# Find the traceId from a session_opened event:
grep 'broker:session_opened' ~/.comis/logs/daemon.log | grep '"agentId":"<your-agent>"' | tail -5

# Then follow all events for that trace:
grep '"traceId":"<your-trace-id>"' ~/.comis/logs/daemon.log | jq -c '{step, event: .["event"] // .["type"], reason: .reason}'
```

Expected sequence for a successful injection:
`session_opened` → `request` → `injected` → (upstream response) → `session_closed`

### Broker: request forwarded but key rejected upstream

If the upstream API returns 401, the secret value may be wrong. Verify:
1. The `secretRef` key in the binding matches the stored secret name.
2. The stored secret value is correct: update it with `secrets_manage set <KEY>`.
3. Check the injection rule kind — `anthropic` preset injects `x-api-key` (raw, not Bearer). For OpenAI-compatible APIs use a custom binding with `format: bearer`.
