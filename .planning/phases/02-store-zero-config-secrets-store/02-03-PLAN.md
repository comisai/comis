<objective>
Wire `keyHex` from `writeMasterKeyIfAbsent` through `bootstrapSecretsAndEnv` into `setupSecrets`
so the encrypted store is usable on the same boot; add the `COMIS_DISABLE_ENCRYPTED_SECRETS`
opt-out flag with a loud WARN.

Purpose: Plans 01 and 02 added the type surface (`keyHex` in core, `seedKeyHex` in memory).
This plan is the daemon-level composition: it re-orders the boot sequence so
`writeMasterKeyIfAbsent` runs BEFORE `loadEnvFile`, captures the freshly-generated `keyHex`,
and threads it into `bootstrapSecretsAndEnv` → `setupSecrets`. It also adds the
`COMIS_DISABLE_ENCRYPTED_SECRETS=1` escape hatch (read via `systemGetEnv` before the
write step) and emits a deferred WARN after logger init if the opt-out is active.

Output:
- `bootFoundation` in daemon.ts: reads opt-out flag early, calls `writeMasterKeyIfAbsent`
  before `loadEnvFile`, captures `autoInitKeyHex`, passes it to `bootstrapSecretsAndEnv`
- `bootstrapSecretsAndEnv` private function: widened to accept `seedKeyHex?: string`
- `DaemonOverrides` in daemon-types.ts: `setupSecrets` type updated to widened signature
- Deferred WARN emitted via `daemonLogger.warn(...)` after logger init (same pattern as
  `permissionCorrections` deferred logging at daemon.ts:1431)
- RED tests: (a) opt-out produces `secretStore: undefined` pre-patch, (b) same-boot produces
  `secretStore !== undefined` pre-patch (both fail before this plan's changes land)
- GREEN tests: both behaviors pass after patch
</objective>

| Boundary | Description |
|----------|-------------|

| writeMasterKeyIfAbsent → bootstrapSecretsAndEnv | `keyHex` is ephemeral 32-byte key material passed in-memory; not set on `process.env` (AGENTS.md §2.2 forbids mutation) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-03-01 | Information Disclosure | `autoInitKeyHex` variable in `bootFoundation` | mitigate | Variable is scoped to `bootFoundation`; NEVER logged (grep gate in verify step); passed only to `bootstrapSecretsAndEnv` as `seedKeyHex`; zeroed out by GC after function returns |
| T-02-03-02 | Information Disclosure | `COMIS_DISABLE_ENCRYPTED_SECRETS` env flag leaking mode to logs | accept | WARN explicitly announces opt-out mode to operators — this is intentional; the flag value itself is not a secret |
| T-02-03-03 | Elevation of Privilege | Operator sets `COMIS_DISABLE_ENCRYPTED_SECRETS=1` while a key is in `.env` | accept | Per locked decision: opt-out always produces `secretStore: undefined` regardless of `.env` state; operator explicitly chose no encryption; WARN includes backup-obligation message; behavior is documented in STORE-04 |
| T-02-03-04 | Information Disclosure | `writeMasterKeyIfAbsent` writes `.env` before `loadEnvFile` — race window | accept | Write is synchronous (`appendFileSync`); `loadEnvFile` runs after in the same synchronous sequence; no concurrent access; file mode 0600 already enforced by `chmodSync` in `writeMasterKeyIfAbsent` |
| T-02-03-05 | Denial of Service | `writeMasterKeyIfAbsent` fails (disk full, permissions) | mitigate | Current implementation throws; daemon throws in `bootFoundation` → `FATAL: Bootstrap failed` → clean shutdown; acceptable: if disk full at boot, daemon cannot run anyway; no key material is lost because the key was never persisted |
</threat_model>
