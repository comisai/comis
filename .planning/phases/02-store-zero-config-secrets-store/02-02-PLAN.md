<objective>
Add `seedKeyHex?: string` fallback to `SetupSecretsOptions` so the daemon can initialize the
encrypted store without a restart when the master key was just auto-generated on first boot.

Purpose: `bootstrapSecretsAndEnv` (daemon.ts) calls `setupSecrets({ env: process.env, dataDir })`.
After Plan 01's `writeMasterKeyIfAbsent` returns `keyHex`, the daemon can pass it as `seedKeyHex`
to `setupSecrets`. Without this parameter, `process.env.SECRETS_MASTER_KEY` is still undefined
(the `loadEnvFile` call hasn't happened yet on the new key path), so `setupSecrets` falls through
to Branch 1 (`ok(null)`) and the store remains unavailable — requiring a restart.

Output:
- `SetupSecretsOptions.seedKeyHex?: string` field added
- `const raw = opts.env.SECRETS_MASTER_KEY ?? opts.seedKeyHex;` replaces `const raw = opts.env.SECRETS_MASTER_KEY;`
- All 4 existing Branch-1/2/3 tests remain green
- RED test: `setupSecrets({ env: {}, dataDir, seedKeyHex: validHex })` returns `ok(null)` on
  pre-patch code — fails because pre-patch ignores `seedKeyHex`
- GREEN tests: same call returns `ok({ crypto, dbPath })` after patch
</objective>
