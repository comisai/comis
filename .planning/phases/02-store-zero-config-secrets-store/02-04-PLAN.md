<objective>
Add a zero-cost pre-flight check in the `env_set` branch of `gateway-tool.ts` that returns a
structured `secrets_store_unavailable` error before the confirmation gate and before any
rate-limit token is consumed.

Purpose: The current flow is: placeholder-rejection → `envSetGate` (confirmation) → `rpcCall("env.set")`.
The `env.set` RPC handler consumes from the 5/min write bucket BEFORE the `!deps.secretStore`
check. This means calling `env_set` with no encrypted store wastes one of 5 tokens/minute and
only fails after the confirmation dance. The fix: call `rpcCall("gateway.status", { _trustLevel })`
first (no rate limit; returns `manifest.secrets.encrypted`). If `false`, return
`{ error: "secrets_store_unavailable", hint: "..." }` immediately. The `env.set` rate-limit
bucket is never touched.

This plan is independent of Plans 01-03 (no shared files) and executes in Wave 1, in parallel
with Plans 01 and 02. It uses the `gateway.status` pre-flight path that the research confirmed
is already present and free of rate limits.

Output:
- Single block inserted in `gateway-tool.ts` before `envSetGate(p)` in the `default:` case
- RED tests: (a) store-unavailable returns `secrets_store_unavailable` error — fails pre-patch
  because no such check exists, (b) two consecutive calls on unavailable store succeed (not
  rate-limited) — fails pre-patch because rate limit IS consumed
- GREEN tests: both pass after patch
</objective>

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-04-01 | Information Disclosure | `secrets_store_unavailable` error revealing store state to agent | accept | `env_set` already requires `_trustLevel: "admin"`; revealing that the store is unavailable to an admin caller is acceptable — they need this information to fix the configuration |
| T-02-04-02 | Denial of Service | Agent spamming `env_set` to consume `gateway.status` calls | accept | `gateway.status` has no rate limit by design (it's a diagnostic endpoint); the `env_set` action itself has `_trustLevel: "admin"` gate (only admin callers can reach this code); rate-limiting admin status checks would degrade legitimate observability |
| T-02-04-03 | Spoofing | TOCTOU: store becomes available between `gateway.status` check and `rpcCall("env.set")` | accept | Window is < 1ms (sequential awaits); if store becomes available between checks, the `env.set` handler's own `!deps.secretStore` check will produce an appropriate error; the TOCTOU window has no security impact |
| T-02-04-04 | Information Disclosure | `hint` message leaking file paths like `~/.comis/.env` | accept | `~/.comis/.env` is documented in public Comis docs as the standard data directory; admin callers already know this; the hint is actionable guidance, not a secret disclosure |
</threat_model>
