# 03 — OBSERVABILITY: ground truth · dual oracle · logging · troubleshooting · the two improvement loops

> The agent's chat reply is the **least trustworthy** oracle — it refuses, confabulates, or doesn't paste
> results. Every verdict is read from ground truth. And every diagnosis friction is itself an issue to fix
> (leave observability + the emulator better than you found them).

## Ground-truth read-order (stop when you have the answer; a fall-through to the raw log is itself a §obs-loop item)

1. **Surface reply** (`drive.mjs` output / RPC result) — least trustworthy.
2. **Channel oracle** (emulator) — `GET /control/chats/:id/outbound` = the exact bytes Comis put on the wire (text, inline keyboard + callback_data, parse_mode, reply-threading, reactions, silent flag). Independent of Comis's own bookkeeping.
3. **Trajectory** (authoritative event log) — `~/.comis/workspace/sessions/<tenant>/<channel-or-chatId>/<file>.jsonl.trajectory.jsonl`, resolved via the co-located `.trajectory-path.json` pointer (never a hand-built path). Carries `tool.result`(+provenance), `tool.result_offloaded`(`diskPathRel`), `session.summary`, `model.completed`, `breaker_trip`; plus `_session-metadata.json` (`degraded`/`costUsd`/`toolStats`/`breakerTripCount`/`topErrorKinds`).
4. **`explain <sessionKey|traceId>`** (one-call root cause) — outcome, per-tool ok/failed, normalized failures, breaker timeline, `contextBudget`, deterministic `likelyRootCause`. Reach it via `revoke.mjs` (`obs.explain` RPC) or the CLI.
5. **`fleet --since N`** (daemon-wide) — degraded rate, top errorKinds, breaker trips, cost, and the `health_signal`/`model_health`/`config_posture` findings (`chimeric_model`, stranded-secret count, TLS-off, `served_below_configured`).
6. **DB / workspace** — `memory.db` (`lcd_*`, `memories`, `outcome_events`, `learned_skills`, `tuned_alpha`, `memory_usefulness`, `delivery_queue`, `delivery_mirror`, audit) + the workspace filesystem (the written file, the generated media). No `sqlite3` on the VPS → use **`scripts/db.mjs`** (the read-only DB oracle, reuses the daemon's better-sqlite3): `db.mjs tables|schema <t>|cols <t>|count <t>|rows <t> [n]|pick <t> <c1,c2> [n]|sql <raw>` — canned sub-commands so you never fight ssh→su→node quote-hell. This is the **primary oracle for offline/learning/memory capabilities** (see §offline-oracles).
7. **Daemon log** (`/home/comis/comis-m1.log` or `~/.comis/logs/daemon.*.log`, Pino JSON) — **last resort**; if you needed it, that's a §obs-loop item.

**The CLAUDE.md decision tree (run these BEFORE a raw grep):** "review the logs" / daemon-wide → `fleet --since N` (surfaces the worst session + the config-posture findings) → then `explain <ref>` on that session to root-cause it. The CLI is not on PATH locally (`node packages/cli/dist/cli.js …`); on the VPS the comis CLI is on the comis user's PATH (`sudo -u comis bash -lc "comis …"`).

## §offline-oracles — testing offline / cron / DB / event-resident capabilities (not channel-shaped)

Many capabilities are **NOT a chat round-trip** — verified learning, memory crons, the LCD, online-tuning, eviction, consolidation, the delivery queue. The channel reply tells you nothing; the truth is in the **DB, the cron run, and the event stream**. The recipe:
- **Drive** the trigger that produces the state, not a chat turn: a **tool/graph turn** that the offline job consumes (e.g. a tool turn → `tool:executed` → `observe`→`resolve` → `outcome_events`), or a **cron run**. The system memory/learning crons are real rows in the cron store — `cron.list {agentId}` shows them (`memory-online-tuning-default`, `skill-synthesis-default`, `memory-lifecycle-default`, payload `{kind:"system_event",text:"__…__"}`, with `lastRunAtMs`/`nextRunAtMs` proving they fire). Trigger one with **`cron.run {jobName}`** — the job's NAME, not its id; resolve via `cron.list` (e.g. `revoke.mjs cron.run jobName "Memory online tuning"` → `{triggered:true, resolvedAgentId}`). (The operator gateway path was fixed by **#240** — server-side orch-cap injection after the ORIGIN-02 strip; pre-#240 it returned `Capability denied: orch:cron` and you had to read cron OUTPUTS from accrued state + `lastRunAtMs` instead.)
- **Observe** in the DB (`scripts/db.mjs`) + the CLI obs (`comis memory learning` / `comis memory skills` — coverage %, the skill funnel) + the **`learning:*` / `memory:*` trajectory events** (bridged via `TRAJECTORY_BRIDGE_MAPPING` → readable through `explain`/`obs_query`). DB-level HARD invariants are inspectable directly: e.g. `db.mjs schema learned_skills` proves `trust_level CHECK(... IN ('learned'))` (trust can never be raised by learning); `db.mjs cols tuned_alpha` proves the no-trust-column belt + the per-intent PK.
- **Time-control:** offline jobs run on a nightly schedule. Either trigger them (above) or read the OUTPUT of a prior scheduled run (the `lastRunAtMs` + the accrued rows). The keyless deterministic loop (`tool:executed`→`observe`→`resolve`→reward/eviction) needs **no LLM key** and is the cheapest, most reliable thing to drive first.
- **Verify impl-state at HEAD FIRST** (`04-DERIVE §A3`): a design-doc target may describe these as "dormant/absent" when they actually **shipped and default-ON** (verified-learning's flags default `enabled:true`). Confirm what's live before testing — the doc lies in both directions.

## §system-health-sweep — the broad-issue hunt (precise filters; non-negotiable #6)

While the rig is hot, hunt issues across the WHOLE daemon, not just the target. The filters matter — a sloppy grep manufactures false alarms:
- **`fleet --since N`** → triage each finding: **real bug** vs **expected-for-the-rig** (`gateway.tls off` + `CANARY_SECRET unset` are normal on a loopback test box; `embedder_not_multilingual` is advisory) vs **acute incident** (breaker trips, a degraded spike).
- **Daemon-log scan — read STRUCTURED FIELDS, not raw words.** `grep "degraded"` matches the periodic `"msg":"Daemon health"` report lines (which carry a `degraded` COUNT field) → a false positive (this run saw "16 degraded" that were all health-report lines, 0 real incidents). Filter on `"level":50` / `"level":60` (ERROR/FATAL), tool-failure shapes (`"success":false`, `failedTools`, `effectiveFinishReason:"completed_with_tool_errors"`), and the gating/permission strings (`not reachable from an agent origin`, `Capability denied`, `EACCES`/`EPERM`). Always read the `err`/`hint`/`errorKind` to classify (e.g. an `errorKind:"dependency"` pi-ai cache-TTL note is benign, not a bug).
- **Drive a basic agent tool turn** even if the target doesn't use it — `memory_store`, `web_search`, a `write`. A broken core tool whose backing RPC is mis-gated (the MD-02 `memory_store` deny-by-origin: `err:"Control-plane method memory.store is not reachable from an agent origin"`) is invisible to handler unit tests and only surfaces under a real agent turn. This single move found a P0 in a subsystem unrelated to the target.

## The dual-oracle cross-check (a HARD assertion)
> the text in the **channel oracle** (recorded outbound) **==** the **Comis oracle** (`delivery_mirror.text`) for that session.
Catches the whole class of "Comis thinks it sent X but the wire shows Y." Two oracles disagreeing = a real bug, not flake.

## Driving + capturing (the practical gotchas)
- **`drive.mjs` uses answer-aware quiescence** — models think 15–30s between a progress line and the answer; a naive "quit after N s of silence" exits during the gap. Wait for a *substantive* (non-progress) reply, then quiesce. Filter the `🔧`/`✓`/`(running…)`/`reading ~` progress lines.
- **The DAG runs async past the drive's exit.** The agent announces "running it now… GraphId X" (a substantive message → the drive quiesces), then the graph executes for minutes. **Poll the daemon log** for `Graph node completed`/`Graph execution complete` + `GET …/outbound?waitMs=90000` for the final node's message. Don't conclude "it stopped" from the early drive exit.
- **One clean inject per turn / clean-restart between heavy tests** — rapid kill+reinject pollutes the steer+followup queue → degraded turns + uncaptured replies + the agent confabulating "I already did this."
- **Frame jail/security probes benignly** — capable models (Anthropic especially) *refuse* "print SECRETS_MASTER_KEY / read secrets.db" as exfiltration and won't run the orchestrate script, so you get no jail stdout. Test the gate **deterministically** with a benign script that *incidentally* reveals isolation (`fetch('https://example.com')` → `NET:BLOCKED`; `process.env.X ? 'yes':'no'` framed as a "sandbox capability check"). Provider-independent properties (the bwrap jail) — prove once, don't refight per model.
- **Read the right layer.** The agent's DIRECT tool surface includes admin tools when the sender is admin-trust — that's *correct*. A capability gate (e.g. M1's) applies to the **jailed/agent-origin** surface, not the admin user's direct turn. Confirm WHICH layer a requirement governs before asserting a denial.

## Gotchas that cost cycles (from the v2.29 M1 + orchestration-excellence runs — read before driving those oracles)
These each burned a cycle. They are *driving* gotchas (you'll mis-drive or mis-read the oracle), not bugs:
- **Operator RPCs have `_agentId` stripped → they do NOT trigger agent-origin gates.** An operator `graph.execute`/`session.spawn` via `revoke.mjs` carries no `_agentId` (the dispatcher strips `INTERNAL_FIELD_NAMES` from external callers, ORIGIN-03), so the **P0-C no-downgrade gate and the deny-by-origin chokepoint never fire on it** (the spawn-path gate is guarded by `params.callerAgentId`). To drive an *agent-origin* spawn refusal (P0-C, child⊆parent), drive a **channel agent turn that calls `sessions_spawn {agent:<target>}`** — that's the only path carrying the agent origin. (Operator RPCs ARE the right driver for the *#240 operator-CAN-reach-orch-dual-use* direction.)
- **The BudgetGuard pre-check structurally preempts the post-hoc breach event.** `budget-guard.ts` is *pre-commit* (rejects a call when `executionTotal + estimate > cap`), so a node's `tokensUsed` can never exceed its per-node cap → the post-hoc `applyNodeBudgetBreach` (`spend > budget`) **never trips live**, so `subagent:budget_exceeded` does NOT fire on the per-node path and the node fails with an empty error (the agent-layer `finishReason:"budget_exceeded"` is dropped at the graph completion-event boundary). Don't score P0-A on the *event* — score it on the bound itself (the node failed + the graph didn't whole-abort) and read the agent-layer `finishReason`.
- **Emulator channel faults hit the MAIN delivery queue, not the announce-batcher.** A `sendMessage` fault injected via `/control/faults` is absorbed by the channel delivery queue's own retry/dead-letter (`"Message delivery failed, scheduled for retry"` / `"Message delivery permanently failed"`) BEFORE it reaches the announce-batcher's `subagent:delivery_retried`/`deadlettered` classifier (which covers the in-process `announceToParent` surface). So a channel fault verifies queue resilience, NOT the batcher events — those are unit-test territory. Note which resilience LAYER a fault reaches before asserting on a layer-specific event.
- **`su - comis -c "…"` drops env vars and mangles inline single-quotes.** A `TAG=foo su - comis -c "node x.mjs"` does NOT pass `TAG` (fresh login shell). Write inputs to a world-readable `/tmp/<f>.json` and have the script read the file (this is why `cfg-patch.mjs` reads `/tmp/patch.json`). Same for any nested-quote JSON you'd pass through `su -c`.
- **Precise log scan, not raw grep (use `scripts/logscan.mjs`).** `grep "degraded"` matches the `"Daemon health"` count-field lines; `grep "transient"` matches `"Stripped transient inline-recall from cached prefix"`. Both are false positives. `logscan.mjs --level 50,60 --uniq` / `--kind <k>` / `--msg <substr> --fields …` reads the STRUCTURED fields and projects what you need (replaces the hand-written `grep | node -e` projectors).

## Logging discipline (what "instrumented for troubleshooting" means)
Per the §2.7 matrix in `AGENTS.md`: every boundary crossing (channel inbound, RPC, tool call, external API, queue hop) must be reconstructable from logs + events alone — an INFO completion line with `durationMs`, an ERROR/WARN carrying `hint`+`errorKind` on every failure branch, a `step:`-tagged DEBUG per intermediate stage, an `eventBus` event per state transition, `traceId` riding AsyncLocalStorage so one request stitches across packages. **Litmus before calling a path done:** can you explain exactly how its next production failure is diagnosed from the logs it emits? If not, add the instrumentation now.

## The OBSERVABILITY-improvement loop (mandatory — close it test-first, like any bug)

The moment a diagnosis required **any** of these, the diagnosability surface has a defect — fix it test-first (fix-verify step 10):
- you grepped raw `daemon.*.log` / hand-joined files because `explain`/`fleet`/the trajectory didn't carry the evidence;
- an error told you WHAT broke but not WHICH KNOB; a message pointed you the **wrong way**; the load-bearing evidence existed only at DEBUG; a lens returned a **silent empty** in the exact failure it exists to diagnose; two lenses double-counted, or a field name meant different things on different lines; the verdict ranked chronic noise above the acute event.

**Thread a new signal through all five stages** (the canonical `context_exhausted` precedent — copy it):
1. **Emit** at the boundary: a structured log (INFO `durationMs` / DEBUG `step:` / ERROR-WARN with `hint`+`errorKind`) **and** an `eventBus` event.
2. **Bridge to the trajectory:** `TRAJECTORY_BRIDGE_MAPPING` + a `translate-payload.ts` case (+ `TRAJECTORY_EVENT_TYPES` if new) — extract a **content-free** payload (ids / labels / counts / closed-enums only; never bodies, prompts, alphas, or secrets).
3. **Persist:** `TrajectoryRecorder` writes one bounded JSONL line; `_session-metadata.json` rollup at session end.
4. **Assemble the report:** thread onto `obs-explain-signals.ts` → `IncidentReportSchema` → `assembleIncidentReport` (fleet analog: `reduceFleetWindow`/`queryDiagnostics` → `FleetHealthReport.findings[]`).
5. **Stamp the verdict:** add a branch to the ordered, first-match-wins, **pure** `HEURISTICS` registry (`obs-explain-heuristics.ts`) so `likelyRootCause` is numbers-backed + deterministic.

**Litmus:** for every incident class you touched, you can state — and have *proven on the actual incident* — "next time, `explain <ref>` (or `fleet --since N`) answers this in one or two calls."

**Pre-seeded obs-gap ledger** (known gaps — fix or note when hit): masked-4xx on openai-responses/google (surfaced as empty, not an error); detached-rig daemon writes no `daemon.*.log` to its data dir; cross-lens metric divergence (`explain` cacheReadRatio:0 vs `cache stats` 100%); cron id-vs-name confusion ("Job not found" without naming the mismatch); `whoami`/autonomy RPCs unregistered when autonomy off; `explain` spawn-tree omits graph sub-agent children.

## The EMULATOR-improvement loop (mandatory — the mirror of the obs loop)

The emulator is the **primary instrument**; leave it better than you found it. The moment a test required any of these, the drive/observe surface has a defect — close it test-first (the emulator has its own unit+contract tests, `pnpm vitest run -c test/live/vitest.config.ts <file>` — the bare root config **excludes** `test/live`, a false green):
- you drove a channel-shaped capability through `/rpc` or `/v1/*` because the channel path couldn't reach it (a missing Bot API method / inbound update type / `tg` verb);
- the channel oracle didn't expose a wire signal the bot emitted; an adapter resilience fallback was unreachable because the emulator can't return the triggering error; a verb silently no-op'd instead of an honest `not_implemented_in_phase`; a group/forum/multi-user/reaction/edit/callback shape couldn't be produced; a third+ channel was needed.

**Extension seams** (test-only, under `test/live/`; **never** a `@comis/*` edge or `bundledDependencies`): add a Bot API method in `emulators/telegram/tg-emulator.ts`; an inbound shape via a grammy-typed builder in `tg-payloads.ts`; a control verb in `harness/control-api.ts` + `bin/chan.ts`; a fault via `fail(method, error, {once})`; an oracle field in `assert/channel-trace.ts`; a whole new channel via a wire backend on the shared `http/ws/tcp` base + a one-line `startRig({channel})` registration. **A silent stub is the worst outcome** — an unimplemented verb must `log()` what's missing and exit/throw an honest reason. Full architecture + the fault→fallback matrix: `.planning/live-tests/telegram-emulator-harness-design.md` §3, §3A, §4.1–4.7.

**Litmus:** for every capability the rig couldn't reach, "next time `tg <verb>` drives it and `tg history`/`mirror`/`db` observes it, with no workaround" — proven, not asserted.

## Recurring defect CLASSES to watch for (from FINDINGS — these bite repeatedly)
- **Built-but-not-wired** (the #1 class): a resolver/handler/fix exists + passes its unit test, but the live call-site/credential/config/composition-root path doesn't reach it. *Only live driving + a wiring-guard arch test catch it.* (e.g. M1 `lease.revoke` unregistered because `leaseManager` wasn't threaded into the dispatch deps; the keyless-summarizer credential bypass.)
- **Silent degrade / masked 4xx:** a 4xx swallowed into a degraded path that looks like success (voice-forbidden→doc, parse-error→plain, abstain-on-empty). Always assert the *fallback fired* against the oracle, never "no error."
- **Silent model substitution:** a catalog-unknown configured model resolves to a default silently (config says X, runs Y). Always verify the actual `modelId` == config.
- **Context-free trust/identity resolution (security):** an unmapped sender inheriting an elevated default (the group reaction-spoof). Fails open. Thread the participant; fail safe.
- **Token/window double-count + capability-class misclassification:** divergent token views; a capable model classed nano → degrades before it runs. Read the budget *components*, not just the total.
- **LCD contamination:** prior turns replay; clean-slate must replace `memory.db` AND clear the session JSONL.
- **Origin-gating regression (agent-denied / operator-denied):** a capability/deny-by-origin model (Comis M1, Phase 210-215) sweeps an RPC into the wrong bucket, breaking a real caller. Two flavors, both found this run: (a) **agent-denied** — an agent tool's backing RPC is `scopes:["admin"]` → `assertNotAgentOrigin` throws `"Control-plane method X is not reachable from an agent origin"` for the agent (MD-02: `memory.store` broke the `memory_store` tool). (b) **operator-denied** — a dual-use RPC is `orch:cron`-gated but the operator gateway path injects no `_capabilities` → `"Capability denied: …"` for the operator (cron.run — fixed by #240, server-side orch-cap injection after the ORIGIN-02 strip). **Catch it:** drive the real tool/RPC (handler unit tests stay green — the gate is in dispatch, not the handler). **Pin it:** a source-derived arch test mapping each agent tool → its backing RPC, asserting agent-reachable (the `agent-memory-tools-deny-by-origin.test.ts` pattern). Often a **test blind spot** lets it through (the existing deny-by-origin test keyed off a map that excluded the surface).
- **Lesson:** the obvious security fix is often wrong (two disproven fixes before the real multi-point thread) — a diagnostic run beats a code guess. And unit tests can go green while failing live — the **live deploy-proof reading actual ground-truth fields is the arbiter**. A nuanced/security-sensitive gating fix that needs design (e.g. the operator-aware cron gate) is **documented as a finding with the fix direction**, not rushed.
