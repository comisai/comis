# Live-test helper scripts — VPS or local rig + channel emulators (Telegram, Microsoft Teams)

Ready-to-run versions of every helper used in the live-test. Read **`../01-SETUP.md`** for the full
setup playbook and **`../03-OBSERVABILITY.md`** for the traps — this folder is the copy-paste toolkit
those docs refer to. (Driven by `../00-MISSION.md`.)

## Running the kit's own unit tests

This folder is its own `live-kit` project in the root `vitest.config.ts`, so the `*.test.ts` helpers here
run in `pnpm test` / `pnpm validate` and a bare `pnpm vitest run <path>` from the repo root works — no
`--config` needed. Two neighbours sit outside that project on purpose: `remote-root.test.ts` needs built
`@comis/*` and runs in the integration tier's aliased `live-scenarios` project, and the `*.test.mjs` files
are `node:test` suites (`node --test <file>`). Always read the test COUNT — zero collected files exits
looking clean, so a mistyped path proves nothing.

## Provider cyber-abuse safety gate

Read **`../CYBER-ABUSE-SUSPENSIONS.md`** before any security, credential, SSRF, destructive,
self-escalation, prompt-injection, sandbox, or threat-hunting drive. The arbitrary provider-backed
injectors run `live-provider-risk-gate.mjs` before network activity and exit `4` on suspended content.
`revoke.mjs` is gated too, on its resolved params, for every RPC except the operational/diagnostic
exemptions — so `graph.execute`, `cron.run`, and `message.send` cannot route around it. That exempt set is
enumerated once in `../CYBER-ABUSE-SUSPENSIONS.md` and is `UNGATED_RPC_METHODS` in
`live-provider-risk-gate.mjs`; every other method is gated by default, and a benign payload classifies
clean and passes.
The driver may declare opaque/risky content with `COMIS_LIVE_TEST_RISK=cyber-abuse`, but must not set
`COMIS_LIVE_CYBER_ABUSE_TESTS=operator-authorized` unless the operator explicitly requested that test in
the current task. Never persist the authorization acknowledgement in `.live-env` or a rendered rig env.

## Two rigs — `RIG_MODE`

| `RIG_MODE=remote` (default) | `RIG_MODE=local` |
|---|---|
| The **production installation** — the systemd + npm-global layout `website/public/install.sh` creates, the same thing users get. Canonical: the only rig that exercises the sandbox/jail, systemd, and `*.linux.test.ts` surfaces. | **This machine**, from this checkout, against an explicitly isolated data dir. No ssh, no deploy — the fast inner loop. |
| Bring up: `install-vps.sh` → `deploy-scripts.sh` → `setup-vps.sh` → `WIRE=1 deploy-emu.sh` | Bring up: **`./init-local-config.sh` → `./local-up.sh`** |

Mode resolution lives in **`_rig.sh`** (shell) and **`_rig.mjs`** (node), so every driver and oracle
below works in both modes unchanged. Only the genuinely rig-shaped steps branch: the deploy family is
remote-only (it says so and exits 0 locally), and the lifecycle scripts swap systemd for an explicit
stop/relaunch. **`../01-SETUP.md §Local mode` states what a local run cannot prove — read it before
recording a local pass.**

## Config and precedence

`cp .live-env.example .live-env` and edit for reusable values. The shell helpers resolve explicit env →
`.live-env` → rendered rig env → defaults; `deploy-scripts.sh`
renders it to the rig env file (**`/root/comis-rig.env`** remotely, **`./.rig-env`** locally), where the
rig-side `.sh` scripts source it and the `.mjs` helpers read it via **`_rig.mjs`**. In remote mode only
`VPS` is mandatory. `local-up.sh` requires explicit absolute `DATA`, free `GW_PORT`, and dedicated
non-`comis` `SERVICE` values so it cannot fall back to an everyday installation:

| Var | Default | Meaning |
|---|---|---|
| `RIG_MODE` | `remote` | `remote` = the VPS production install · `local` = this machine. An unknown value is a hard error, never a silent fallback to `remote` |
| `VPS` | _(set in `.live-env`)_ | ssh target `user@host`; ssh KEY lives in your `~/.ssh`. **Remote mode only** |
| `LOCAL_SUPERVISOR` | `auto` | local mode: `auto` (pm2 when it manages `$SERVICE`, else tmux when installed, else direct) · `pm2` · `tmux` · `direct` |
| `EMU_GROUPS` | _(unset)_ | JSON array of group chats to pre-create AT EMULATOR LAUNCH (they cannot be created over `/control`) — required for any group/mention arc |
| `REMOTE_SUDO` | `0` | set to `1` when the SSH target is a deployment user with passwordless `sudo -n` |
| `COMIS_USER` / `COMIS_HOME` | `comis` / `/home/comis` | the dedicated service user install.sh creates + its home |
| `DATA` | `/home/comis/.comis` | the daemon data dir (config, secrets, sessions) |
| `PKG` | `/home/comis/.npm-global/lib/node_modules/comisai` | the installed package root — daemon/CLI dist under `$PKG/node_modules/@comis/` |
| `SERVICE` | `comis` | the remote systemd unit name; local-up requires a dedicated non-default name |
| `GW_PORT` | `4766` | gateway port |
| `GWTOKEN` | _(per box; fetch: `ssh $VPS "su - comis -c 'comis secrets get COMIS_GATEWAY_TOKEN'"`)_ | the RESOLVED gateway bearer token for the raw RPC helpers |
| `CHATID` | `678314278` | the emulator chat/sender id to drive |
| `EMU_DIR` | `/root/comis-emu` | emulator tree on the box |
| `MODELS`/`PRIMARY` | — | the model list + restore-target for `models-sweep.sh` |

The two provider-risk variables are intentionally absent from this reusable table: the risk declaration
belongs on a specific command, and the operator acknowledgement must never become ambient campaign state.

## Run order

```bash
# 0. (Re)install THIS checkout onto the VPS through the REAL installer — fresh box (full bootstrap:
#    deps, comis user, systemd unit) and existing box (in-place upgrade) alike; restarts + boot-verifies:
bash test/live/self-driving/scripts/install-vps.sh        # SKIP_BUILD=1 to reuse the local dist

# 1. Push the WHOLE kit + the rig env to the box (re-run every session — the box drifts from the kit):
bash test/live/self-driving/scripts/deploy-scripts.sh     # auto-fetches GWTOKEN from the box if unset

# 2. ONCE per box — emulator runtime (tsx) + chown leftovers + layout sanity:
ssh root@<vps> 'bash /root/setup-vps.sh'

# 2b. FRESH box only (install ran --no-init → no config): render a rig-ready config.yaml + token + master key:
ssh root@<vps> 'PROVIDER=anthropic MODEL=claude-sonnet-4-6 node /root/init-config.mjs'
# then give it provider creds:  ssh root@<vps> "su - comis -c 'comis secrets set ANTHROPIC_API_KEY'"

# 3. Emulator: deploy + (re)launch + WIRE the daemon to it (config backup kept) + restart:
WIRE=1 bash test/live/self-driving/scripts/deploy-emu.sh

# 4. Confirm the rig is coherent + serving this build BEFORE driving (both read-only, both name their fix):
bash test/live/self-driving/scripts/rig-doctor.sh
bash test/live/self-driving/scripts/verify-build.sh       # + <symbol> [pkg] to grep your diff in the deployed dist

# 5. Iterate: after each local `pnpm build`, overlay the dist + restart (seconds):
bash test/live/self-driving/scripts/deploy-dist.sh
# root SSH target:
ssh root@<vps> 'bash /root/restart-daemon.sh'
# REMOTE_SUDO=1 deployment target:
ssh <user>@<vps> 'sudo -n bash /root/restart-daemon.sh'

# 6. Clean-slate between reproductions (wipe test state; keeps config/secrets):
ssh root@<vps> 'WIPE_CRONS=1 bash /root/clean-restart.sh'

# Initial clean slate for a stateful relationship; later clean-restart attempts refuse this DATA root.
ssh root@<vps> 'WIPE_CRONS=1 PROTECT_CONTINUITY_AFTER_RESTART=1 bash /root/clean-restart.sh'

# 7. Drive + oracles (the .mjs helpers self-serve env from /root/comis-rig.env):
ssh root@<vps> 'node /root/drive.mjs 678314278 "reply with PONG42"'
ssh root@<vps> 'node /root/revoke.mjs capabilities.introspect'
ssh root@<vps> 'MODELS="claude-sonnet-4-6 claude-opus-4-8" PRIMARY=claude-sonnet-4-6 nohup bash /root/models-sweep.sh >/root/sweep.out 2>&1 &'
```

### Run order — LOCAL rig (`RIG_MODE=local`)

No install, no push, no ssh: the checkout IS the build and this directory IS the kit.

```bash
cd test/live/self-driving/scripts

# 0. Bootstrap each isolated root once; generated credentials enter the encrypted store and are never printed.
RIG_MODE=local DATA="$HOME/.comis-live" GW_PORT=4767 SERVICE=comis-local-drive ./init-local-config.sh

# 1. One command: validate config → build → emulator → wire → scoped daemon → rig-doctor.
RIG_MODE=local DATA="$HOME/.comis-live" GW_PORT=4767 SERVICE=comis-local-drive ./local-up.sh

# 2. Iterate: edit packages/*/src → rebuild → restart (the daemon holds its dist in memory here too)
pnpm build && ./restart-daemon.sh
./verify-build.sh                                       # is dist newer than src? did the daemon pick it up?

# 3. Re-launch the emulator after editing test/live/ (the port changes → re-wire + restart):
./restart-emu.sh && node ./wire-emu.mjs && ./restart-daemon.sh

# 4. Clean-slate between reproductions — ⚠ REALLY deletes $DATA sessions/memory.db/logs:
WIPE_CRONS=1 ./clean-restart.sh

# Initial clean slate for a stateful relationship; use restart-daemon.sh after this.
WIPE_CRONS=1 PROTECT_CONTINUITY_AFTER_RESTART=1 ./clean-restart.sh

# 5. Drive + oracles (identical helpers, no ssh):
node ./drive.mjs 678314278 "reply with PONG42"
node ./revoke.mjs capabilities.introspect
node ./db.mjs sql "SELECT COUNT(*) FROM lcd_messages"

# 6. Confirm the everyday DATA root, real Telegram config, and service were never touched.
```

## Artifact-to-action runtime redrive

`artifact-to-action-runtime-drive.mjs` redrives the `artifact-to-action` sim workload against a real Comis
daemon with **NO model**; `artifact-to-action-drive-oracle.mjs` is the decision layer it imports, split out so
the harness's own guarantees are testable without booting a daemon (`artifact-to-action-drive-oracle.test.ts`
is that gate). The recorded per-variant figures and the evidence boundary belong to the workload and live in
[`../sim/README.md`](../sim/README.md); this section owns the harness contract.

```bash
pnpm build          # it runs THIS checkout's packages/daemon/dist
node test/live/self-driving/scripts/artifact-to-action-runtime-drive.mjs \
  [--variant A|B|C|A-degraded] [--data <NEW-abs-dir>] [--keep]
```

**What it drives.** An ISOLATED daemon — fresh `mkdtemp` data root, own kernel-allocated loopback gateway —
with the workload registered through `integrations.mcp.servers` and its tools pinned past the MCP active-tool
budget (`deferredTools.neverDefer`). Every completion request is answered by a local OpenAI-compatible server
whose next tool call is COMPUTED FROM THE PRIOR TOOL RESULTS, so the drive is deterministic and offline: same
input → same trace. The scripted policy (`nextCall`) carries the per-artifact-kind provenance map every world
variant needs — an unclassified artifact kind, or a required-field set the map does not cover, is REJECTED,
never guessed.

It prints one JSON record: discovered tool count, dispatched tool order, durable `tool.result` count, session
rollup (`endReason`/`degraded`/`toolStats`), `obs.explain` outcome, `sessionKey`/`traceId`/`runId`, the
simulator's terminal grade, and the `failures` that block publication.

**Exit contract — exit 1 unless the run is evidence**, so a dead drive can never read as green. Any of these
fails it: an in-band `agent.execute` error · an absent or non-`success`/1 grade · a wrong commit/readback for
the variant · a run in which the runtime accepted no tool call at all · a trajectory that does not carry one
`tool.result` per dispatched call under THIS run's trace · a rollup that ended other than `success` or did not
carry an explicit `degraded: false` · an `obs.explain` outcome whose severity is not `ok`. A harness-side
failure — a world the scripted policy cannot classify, or a completion request that offered no tool matching
the next step — is reported separately as `policyError`, naming tool discovery and the `neverDefer` pinning
rather than the agent RPC. Preflight exits 2 *before* any daemon, port or data root is acquired: an unbuilt or
partially built checkout names the missing entry point, and a `--variant` the workload does not ship names the
worlds it does.

**Run binding.** Evidence is bound to the invocation by a pre-run watermark on the rollup
(`selectRunRollup`) plus that rollup's own trajectory pointer (`resolveTrajectoryPath`), and the durable
records are filtered to this run's trace (`traceBoundToolResults`) before `driveFailures` renders the publish
verdict. The gateway token's secret is generated per run, so the throwaway loopback gateway is never reachable
with a value from this repository; the session key hashes the token's ID and stays stable across reruns.

**Bounded waits.** `monitorChildLifecycle` turns an `error` or early `exit` from the daemon into an immediate
abort of the active readiness or durability wait, retained as the failure reason — and cleanup then recognizes
that the child is already settled instead of waiting for another exit. Every wait also carries a budget: the
polled readiness, discovery and durability waits (`waitFor`) and the two single-shot RPCs, the agent turn and
the incident explanation (`awaitBounded`). A daemon that stays alive but stops answering therefore ends the
run with a named timeout instead of holding the drive, the daemon and the temp data root open until an
operator interrupts.

**Data root + kept evidence.** `--data` must name a NEW directory outside the checkout and outside
`~/.comis`; cleanup (`createDataRoot`/`disposeDataRoot`) removes only a root this run created (marker-guarded)
and only after the daemon has exited. `--keep` preserves it, and only a clean drive disposes of it. **Every run
that keeps its root — a failed drive, or a clean one under `--keep` — prints a copy-pasteable
`explain --offline` command naming that root and, once the run produced one, its own `traceId`**: the
trajectory, rollup, `logs/daemon.*.log` and `memory.db` in it are what answer WHY a rollup ended degraded, so
the failure path prints the daemon log tail instead of deleting its own evidence. `--offline` is load-bearing in that hint —
without it the CLI opens the gateway first, and on a box already running a daemon the report comes back from
that unrelated daemon for a session it never saw.

**What it proves:** the runtime's transport, tool discovery, tool dispatch and session/observability wiring —
**NOT** model reasoning or learned transfer, because the tool order is scripted.

## Gotchas (don't re-discover)
- **`db.mjs count vec_memories` / `vec_learned_skills` fails `no such module: vec0`** — `db.mjs`'s plain better-sqlite3 handle doesn't load the sqlite-vec extension, so the `vec0` virtual tables are unreadable. To check the **vector+FTS reconcile** on a forget/delete (REC-3), count the plain **shadow** table `vec_memories_rowids` (and `memory_fts`) instead — they drop in lockstep with `memories`. (A kit improvement would be to load the vec extension in `db.mjs`, or add a `veccount <t>` that reads the `_rowids` shadow.)
- **`db.mjs sql "… WHERE x='lit'"` dies `unrecognized token: "\"`** — single-quoted SQL string literals don't survive the `ssh → su - comis -c "…" → node` quoting layers (the `\x27`/`'…'` escapes mangle). Prefer **`db.mjs pick <t> <cols> [n]`** (no literals) and filter/grep the JSON locally, or write the query to a `/tmp/q.sql` file and have `db.mjs` read it. Numeric/no-literal `sql` (e.g. `SELECT DISTINCT session_id FROM outcome_events`) is fine.
- **`logscan --msg <substr> --fields a,b` often prints `{}`** — `--msg` matches by substring so it catches the WRONG lines (`--msg completed` matches "Request completed"/"RPC call completed"; `--msg outcome`/`recall`/`memory_store` matched lines without those fields), and the `--fields` projection only reads TOP-LEVEL keys, returning `{}` when the field is nested or absent. When it returns `{}`, fall back to a **traceId-anchored raw grep** + `node -e` JSON.parse to read the real `err`/`hint`/`errorText` (the tool-failure errorText lives on a `level:40/50` `module:agent` "Tool execution failed" line, NOT on the `module:skills` audit line). A kit improvement: make `--fields` walk nested paths + tighten `--msg` to anchored/exact.
- **Skill-synthesis `admitted:0` is NOT "needs more corroboration" at HEAD — it's an embedding-injection gap** (embeddings never injected → all singletons). See `targets/EXAMPLE-verified-learning.md` + `runs/FINDINGS-LEDGER.md`. Don't re-investigate.

## Notes
- The **Telegram emulator** is `tsx test/live/bin/vps-emu.ts` — deploy + launch + wire with
  `WIRE=1 deploy-emu.sh`. It writes `EMU_JSON` (`$DATA/emulator-wiring.json` locally,

  INVERSE of Telegram — the daemon EXPOSES the inbound webhook and POSTs OUTBOUND to the Connector — so there
  is no `apiRoot` config key. Instead the launcher writes `/tmp/comis-msteams-emu.json` (`{apiRoot, appId,
  tenantId, jwksPath, daemonEnv}`) + the public JWKS to `jwksPath`, and you boot the daemon with the two
  OFF-BY-DEFAULT env seams it prints under `daemonEnv`: `COMIS_MSTEAMS_TEST_JWKS` (local-JWKS ingress
  validator) and `COMIS_MSTEAMS_TEST_CONNECTOR` (redirect Connector egress → the loopback emulator). Neither
  relaxes a security control (see `docs/channels/msteams.mdx#local-emulator-self-drive-testing`); with them
  unset the daemon is byte-identical to production. `msteams-drive.mjs` reads that info file. Under systemd,
  set test env seams in `/etc/comis/env` (the unit's EnvironmentFile) — a shell `export` does not reach the
  service.
- `GWTOKEN` is NOT committed — set it per box in `scripts/.live-env` (gitignored; fetch via
  `comis secrets get COMIS_GATEWAY_TOKEN` — see `.live-env.example`), then `deploy-scripts.sh` renders it
  into `/root/comis-rig.env` (0600) for the box side.
